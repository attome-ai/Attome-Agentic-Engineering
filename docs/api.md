# API

Generated by `python -m structura.app.rest --docs` from the tool schemas; do not edit by hand.

Four doors, one engine:

| Door | Start | Use |
|---|---|---|
| MCP | `python -m structura.agent.mcp_server` | any MCP client (Claude Code, Claude Desktop) |
| REST | `python -m structura.app.rest` | scripts and other programs; `GET /openapi.json` |
| Python | `from structura import Study` | notebooks |
| CLI | `python -m structura.cli run spec.json --accept` | batch runs and CI |

## REST example

```
curl -X POST http://127.0.0.1:8765/api/tools/derive_load -H "Content-Type: application/json" -d '{"mass_kg": 20}'
```

## Python example

```python
from structura import Study
study = Study.from_spec("docs/examples/bracket_20kg.json")
study.accept("me")
study.optimize(budget=120)
best = study.recommended()
print(study.verify(best["params"])["grade"])
print(study.report())
```

## CLI example

```
python -m structura.cli run docs/examples/bracket_20kg.json --accept --budget 120 --out runs/my_study
```

## Tools

### accept_spec

Record that the user accepted the current spec card. Call only with the user's explicit answer; optimization refuses to start without it. A new spec version needs a new acceptance.

| Argument | Type | Required |
|---|---|---|
| `study_id` | string | yes |
| `accepted_by` | string | yes |
| `note` | string | no |

### add_face

Name one more face of an uploaded part family (for a load or support the user chose), by its face id from upload_part.

| Argument | Type | Required |
|---|---|---|
| `family` | string | yes |
| `face_id` | integer | yes |
| `name` | string | yes |
| `doc` | string | no |

### add_lightening_pocket

Redesign an uploaded part (A3): add a lightening pocket cut down from one of its top (+z) planar faces, with length, width and depth as free parameters bounded by that face, leaving `margin_mm` of wall around it. Frozen interfaces (material around every detected hole) are enforced by the gate. Then create a study on the family with these parameters free; mass vs safety factor trades how much material the pocket removes.

| Argument | Type | Required |
|---|---|---|
| `family` | string | yes |
| `face_id` | integer | yes |
| `margin_mm` | number | no |
| `floor_mm` | number | no |

### build_report

Write the interactive study report (one offline HTML file: 3D fields, Pareto explorer, comparison with the baseline, trust panel, history, timeline). Give the baseline design's parameters when there is one. Returns the file path to give the user.

| Argument | Type | Required |
|---|---|---|
| `study_id` | string | yes |
| `baseline` | object or null | no |

### check_feasibility

Check whether any design within the spec's bounds can meet the requirements (evaluates the most- and least-material corners). If infeasible, report the requirement and the best achievable value, and propose the smallest relaxation.

| Argument | Type | Required |
|---|---|---|
| `study_id` | string | yes |
| `mesh_size` | number | no |

### choose_print_direction

Choose the print direction for a design: each of the six axis directions with its tension across the layers (printed parts are weakest there) and support volume, the recommended one and why. Set the spec's print_direction to it before a final verify. Example: choose_print_direction('s1', {'thickness': 8, ...}).

| Argument | Type | Required |
|---|---|---|
| `study_id` | string | yes |
| `params` | object | yes |

### compose_candidates

Best of N (B1): propose several candidate design graphs for the study's brief at once (3-5 is typical). Each is built, gated and solved once at its default parameters against the study's spec; they come back ranked (gate pass, then meets every requirement, then the first objective) with the reason each loser lost. Every graph needs the face names the spec's load cases use and parameters with bounds; the winner's family name can go into a new spec version (family + its parameters as free_params) for the optimizer.

| Argument | Type | Required |
|---|---|---|
| `study_id` | string | yes |
| `candidates` | array | yes |
| `mesh_size` | number | no |

### compose_design

Build a design from a design graph (JSON) or a family with parameters, and run the geometry gate. Returns volume, named faces and gate reasons. Use describe_grammar for feature types. Errors are typed: graph (bad value or reference), compile (geometry failed; names the feature), gate (shape rejected; reasons say why).

| Argument | Type | Required |
|---|---|---|
| `family` | string or null | no |
| `params` | object or null | no |
| `graph` | object or null | no |
| `study_id` | string or null | no |

### create_study

Create a study from a DesignSpec (JSON object). The engine validates it against the family, the materials table and the known quantities (mass_g, max_von_mises_MPa, max_disp_mm, safety_factor, first_frequency_hz, buckling_factor, peak_temperature). Every requirement needs an id (R1, R2, ...) and a source (brief sentence or 'default: ...'). See docs/examples/bracket_20kg.json for a complete spec. Returns the spec card to show the user.

| Argument | Type | Required |
|---|---|---|
| `spec` | object | yes |
| `study_id` | string or null | no |

### derive_load

Turn a mass in a use case into a design force with the working shown, e.g. derive_load(20, 'variable_action', supports=2) -> 98.1 N per bracket, factor 1.5 (EN 1990). Cases: static, variable_action (people, stored goods), permanent_action, sudden_application. Use the returned spec_hint for the load and factor_range; never invent a factor.

| Argument | Type | Required |
|---|---|---|
| `mass_kg` | number | yes |
| `case` | string | no |
| `supports` | integer | no |

Example body: `{"mass_kg": 20}`

### describe_grammar

Describe the design-graph grammar: every feature type with its parameters, kinds and bounds. Use before compose_design.

Example body: `{}`

### evaluate_design

Evaluate one candidate against the study's spec: build, gate, mesh, solve every load case at its worst factor, check every requirement. Use for a baseline or a user-proposed design; do not use it to search (run_optimization does that).

| Argument | Type | Required |
|---|---|---|
| `study_id` | string | yes |
| `params` | object | yes |
| `mesh_size` | number | no |

### explain

Explain two designs (trial numbers): which parameters differ and how each objective moves. Turn the data into one paragraph for the user.

| Argument | Type | Required |
|---|---|---|
| `study_id` | string | yes |
| `trial_a` | integer | yes |
| `trial_b` | integer | yes |

### fit_part_to_family

Check whether an uploaded STEP part matches a part family: the family's closest design and its overlap with the part (intersection over union; 0.95 or more counts as a fit). A fit means the family's parameters can be optimized instead of cutting pockets into the solid. Example: fit_part_to_family('part.step', 'bracket').

| Argument | Type | Required |
|---|---|---|
| `step_path` | string | yes |
| `family` | string | yes |

### freeform_cad

LAST RESORT for shapes the design grammar cannot express (B1): write CadQuery code that assigns the final solid to `result` (cq is imported; units mm). It runs in its own process with a time limit, is exported to STEP, inspected like an uploaded part (holes frozen, faces named) and checked by the geometry gate. Returns the gate verdict, the detected faces and holes, or a structured error to repair. The shape is fixed: optimize it afterwards with the uploaded-part operations (add_lightening_pocket) or by revising the code. Prefer compose_design whenever the grammar can express the part.

| Argument | Type | Required |
|---|---|---|
| `code` | string | yes |
| `name` | string | yes |
| `timeout_s` | number | no |

### get_job

Progress of a background optimization job: state (running, done, error), trials so far and feasible count.

| Argument | Type | Required |
|---|---|---|
| `job_id` | string | yes |

Example body: `{"job_id": "<from run_optimization>"}`

### get_results

Results of the study: feasible Pareto front (each point's parameters and objectives), the recommended knee design, and counts by status.

| Argument | Type | Required |
|---|---|---|
| `study_id` | string | yes |

### list_families

List part families: parameters (unit, bounds, integer), named faces for loads and supports, and what each family is for. Example: list_families() -> [{name: 'bracket', parameters: {thickness: {low: 3, high: 12, unit: 'mm'}}, faces: ['mount_holes', 'load_face', ...]}]

Example body: `{}`

### manufacturing_advice

Manufacturing check and cost for one design of the study's family: FDM printing (build volume, minimum wall, overhang, support volume per print direction, time, cost) and 3-axis CNC (undercuts, internal corners against the tool, stock, time, cost), with advice on which process fits and which rule is closest to its limit. Every rate and price comes from data/processes.json and is an assumption the user should replace with their own; say so when quoting a cost.

| Argument | Type | Required |
|---|---|---|
| `study_id` | string | yes |
| `params` | object | yes |
| `material` | string or null | no |

### model_route

Which model to use for an agent step (plan, spec_extraction, compose, repair, log_parsing, report_drafting, explanation), given how many provider calls for this step have failed. Two failures move the step to the next model on its route; returns exhausted when none is left.

| Argument | Type | Required |
|---|---|---|
| `step` | string | yes |
| `failures` | integer | no |

### plan_study

Record the study plan before running anything: family, physics, objectives and evaluation budget, in one sentence each. Example: plan_study(study_id, family='bracket', physics='linear static', objectives='min mass, max safety factor', budget=120)

| Argument | Type | Required |
|---|---|---|
| `study_id` | string | yes |
| `family` | string | yes |
| `physics` | string | yes |
| `objectives` | string | yes |
| `budget` | integer | yes |
| `notes` | string | no |

### propose_relaxation

When check_feasibility says infeasible: draft the smallest relaxation that makes the spec feasible, as a new spec version with a diff. It is NOT accepted: show the diff, let the user choose (relax, change material or family, or stop), then call accept_spec only with their answer.

| Argument | Type | Required |
|---|---|---|
| `study_id` | string | yes |
| `mesh_size` | number | no |
| `margin` | number | no |

### rank_questions

Rank the brief's unknowns by how much they change the design before asking the user anything. Give the draft spec and a list of unknowns, each {name, question, low: {...}, high: {...}} with edits load_scale, add_load [fx,fy,fz] fraction, material, or factor. Returns at most three questions worth asking, each with its stake; default the rest and say so.

| Argument | Type | Required |
|---|---|---|
| `spec` | object | yes |
| `unknowns` | array | yes |
| `quantity` | string | no |

### record_usage

Record the tokens one model call used, so the study reports them per step (and cost, only when prices are stated in data/model_routes.json). Example: record_usage('s1', 'compose', 'claude-opus-5-5', 3200, 900). Returns the study's totals and whether it is over its token cap.

| Argument | Type | Required |
|---|---|---|
| `study_id` | string | yes |
| `step` | string | yes |
| `model` | string | yes |
| `input_tokens` | integer | yes |
| `output_tokens` | integer | yes |
| `seconds` | number or null | no |

### render_views

Look at a design before solving it (B1 visual review): renders front, back, left, right, top and isometric views with the overall size, from a family (+ params) or a design graph. Returns the image and its file path. Check it against the brief: right overall shape, holes where expected, no stray or floating bodies, plausible proportions. Reject and revise candidates that do not match before spending solver time on them.

| Argument | Type | Required |
|---|---|---|
| `family` | string or null | no |
| `params` | object or null | no |
| `graph` | object or null | no |
| `title` | string | no |

### run_optimization

Start the optimization in the background (method chosen from the budget unless given: botorch_qnehvi, nsga2, nsga3, random). Refuses until the user accepted the spec. Returns a job id; poll get_job. Typical: budget=120, mesh_size=6 for the search.

| Argument | Type | Required |
|---|---|---|
| `study_id` | string | yes |
| `budget` | integer | no |
| `method` | string or null | no |
| `mesh_size` | number | no |

### steer

Steer the search toward a preference. Give `reference` (target value per objective, in the spec's objective order) or `preference` text such as 'lighter, even if it bends more'. Hard requirements still apply. Runs n_trials focused evaluations.

| Argument | Type | Required |
|---|---|---|
| `study_id` | string | yes |
| `preference` | string or null | no |
| `reference` | array or null | no |
| `n_trials` | integer | no |

### upload_part

Upload a STEP part to analyse or improve (A3). Stores it, detects its interfaces (holes and hole patterns, large planar faces, envelope) and writes a part family 'uploads/<name>' that imports it, with those faces named. Show the user the holes and faces, ask which carry the load and the supports and which interfaces must stay unchanged, add any face they name with add_face, then create a study on that family. With no free parameters the study analyses the part as-is (evaluate_design with params {}) and becomes the baseline of a redesign.

| Argument | Type | Required |
|---|---|---|
| `step_path` | string | yes |
| `name` | string | yes |

### verify

Verify a design: three mesh levels, numerical error bars (GCI), equilibrium and energy checks, assumptions and a grade (A/B/C) written by the engine to trust.json. Report the grade and any 'not proven' requirement to the user.

| Argument | Type | Required |
|---|---|---|
| `study_id` | string | yes |
| `params` | object | yes |
| `fine_mesh` | number | no |
